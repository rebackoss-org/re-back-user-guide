    Inheritance workflow¶

    Inheritance adopts a machine that is already backing up to your account. The new install takes over that machine's identity, its ledger of what has been sent, and its drive list — so the server sees a machine it already knows, and only new or changed files get uploaded. Nothing is re-uploaded and nothing already on the account is moved or deleted.

    Use it when you are retiring the machine that used to back up: another PC, a Windows box you are moving off, a reinstall of the same host.

    What inheritance is for¶

    • Move a backup to new hardware. The new machine keeps the old machine's file history instead of starting a second, duplicate set of files.
    • Move a backup to another OS. A Windows install's C: and D: drives can be presented from a Linux box without the server noticing the difference.
    • Recover from a broken install. If the local state is lost but the account still has the machine, inheritance pulls the state back down.

    What comes across¶

    Inheritance moves the record of the backup, not the files:

    item carried notes
    machine identity (host GUID, account binding) yes the account keeps seeing one machine, not two
    ledger of every file already sent yes seeded into the local index, so nothing is re-uploaded
    drive list and volume IDs yes the folders holding those drives are chosen in step 3
    server-side file numbering yes new files continue above the inherited counter
    the backed-up files themselves no they stay on the account; use Restore to get them back
    the source's encryption key or passphrase no if the source used private encryption, keep that key — restores still need it
    your exclude rules, schedule and other local settings no this install's own settings are left alone

    The source machine is retired on the account when the transfer commits: it shows up renamed old_inactive_… and marked as divorced. Do not start its client again — inheritance pauses this install, but the server is never told anything, so a source that kept running would still be pushing under the same backup.

    It is not a restore. Inheritance brings across the record of what is backed up; restoring brings back the files themselves. If you want files back, use Restore.

    Before you start¶

    • Sign in with your account password. Inheritance asks the server for your machine list, and that call needs the password — a session that was restored from a saved key cannot do it. Sign in on the machine card first.
    • The target machine must have no backup identity yet. If it already backs up, the button is greyed out with a ? next to it: clear the current backup state first (see Clearing backup state).
    • The source machine must still be listed on the account. Inheritance reads the source's state archive from the server. Machines that cannot be inherited are shown greyed out in the picker with the reason.
    • Quit the source's backup client first. It is retired on the account once the transfer commits, and nothing here can pause it remotely.
    • Have the folders ready. The last step asks where each of the source's drives lives on this machine. You can also skip a drive and map it later.

    Inheritance pauses backups. It does that locally — the daemon is not started and nothing is sent — so the old and new machine can never both push. The server is not told anything about being paused.

    Step-by-step¶

    1. Pick the machine to inherit from¶

    On Home, in the machine account card, press Inherit existing backup. Choose the source machine from the dropdown and press OK.

    The source's name is not reused: a throwaway host is registered for the transfer (tmp-inhrt-…), and the server retires it once the state has been committed. If the transfer fails before that point, the throwaway host is kept so you can retry without starting over.

    2. Wait for the transfer¶

    The wizard shows the download, the commit and the adoption as they happen: archive size, ledger file and line counts, then the index seeding. Backups stay off for the whole step.

    If it fails, backups stay off and the error is shown with the server's reason. Press OK again to retry — a retry after the commit never re-commits the archive, so a half-finished transfer cannot double-apply.

    3. Map the source's drives to folders here¶

    The state archive knows the source's drives (C:, D:, …) but not where those drives live on this machine, so this is the last step and it cannot be asked earlier. Each drive is listed with the number of files the inherited ledger has for it; type the folder that drive's root is mounted at.

    The drive letter is the identity. A file at /mnt/nas/movies/a.mkv on this machine, with D: mapped to /mnt/nas, is still presented to the server as:

    D:\movies\a.mkv

    That is byte-for-byte the path the old machine used, so the server recognises the file instead of uploading a copy. Ledger paths are never rewritten — only the root folder is local. Both of these are the same mapping:

    This machine D: mapped to Presented as
    /mnt/nas/movies/a.mkv /mnt/nas D:\movies\a.mkv
    /mnt/win-d/movies/a.mkv /mnt/win-d D:\movies\a.mkv

    Rules the wizard enforces:

    • One folder per drive, never nested. A file belongs to the first root that contains it, so D: inside C:'s folder would file one drive's data under the other's identity. Overlapping roots are refused.
    • The folder must exist and be readable. A path that is not there now would fail the first backup anyway.
    • Blank means skip. A drive you leave empty keeps its identity and its backed-up files, but nothing under it is walked here. Its files stay on the account; a restore of those files will ask you for a destination.
    • At least one drive has to be mapped. Skipping all of them would finish the inherit with nothing to back up, so it is refused — clear the backup state instead if you meant to abandon it.
    • One folder per drive letter, and not a folder this machine already backs up: two roots over the same files would present them twice.

    Press Save mapping. The gate clears, the daemon starts and the index is rebuilt from the inherited ledger against the folders you chose.

    Verifying the result¶

    • Home shows the source machine's identity, not a new one, and the backup state is no longer paused.
    • Backup → status reports a file check that is clean rather than frozen, and the file and byte totals match what the account already had.
    • Run one backup. It should send nothing (or only what changed since the source last ran) — if it starts uploading the whole corpus, the drive mapping is wrong: the paths it is producing do not match the ledger.

    Troubleshooting¶

    The button is greyed out. Hover the ? beside it. Either you are not signed in with a password, or this machine already has an identity — clear the backup state first.

    It stopped at "waiting for a local folder". The identity and ledger are adopted; only the drive mapping is left. Reloading the page returns to the mapping pane. It is also reachable headlessly: GET /api/v1/inherit/status lists the pending drives (each with its letter, file count and volume ID), and POST /api/v1/inherit/map takes one decision per drive — a folder, or "skip": true:

    {
  "volumes": [
    { "vol_guid": "v000…123", "path": "/mnt/win-d" },
    { "vol_guid": "v000…456", "skip": true }
  ]
}

    Every pending drive needs a decision (incomplete_mapping otherwise), and a rejected mapping applies nothing. A successful call clears the gate and starts the daemon, exactly as Save mapping does. Like every other step that changes state, inherit/map needs this app's session cookie (inherit/status does not), so sign in first or send the same session the web UI uses.

    It failed before finishing. Backups stay off and the throwaway host is kept. Press OK to retry. If the retry cannot proceed, clear the backup state and start again.

    A mapped drive says its folder is not readable. Fix permissions on the host, then re-enter the path. Nothing was applied — a mapping is all or nothing.

    The first backup wants to upload everything. The mapped root does not correspond to the drive's real contents, so the relative paths do not line up. Remove the mapping and point the drive at the folder that actually holds its tree.

    Backups stay frozen after a successful inherit. The account holds an older, larger copy of a file-check manifest than the inherited ledger rebuilds. The client declares the shrink to the server instead of re-uploading; if a run still reports bzcf_shrunk_on_client, update the client and re-run.

    You added a file on a day the source already backed up. Nothing to do. A manifest the account already holds may not be re-sent smaller, and ours rebuilds denser than the other client's, so the client re-encodes that day's manifest with weaker compression until it clears the held size — logged as bzcomb grow <date>: rebuild … re-encoded … — and uploads it. The records are unchanged; only the compressed bytes differ. A day with no new files is still only declared, never uploaded.

    Clearing backup state¶

    Backup settings → Dangerous → Clear backup state resets this machine: the identity, the ledger, the scan index, the account and host binding, the inherit record, and the encryption settings — including the passphrase and the key that wraps your file keys. The daemon stops. Type CLEAR BACKUP to confirm.

    It keeps what describes what to back up: the volume list with its paths, drive letters and volume IDs, the include/exclude rules, the schedule, the run history and the logs.

    It does not delete backed-up data. Files already on the account stay there and belong to the account, not to this install. Encrypted files whose passphrase you just discarded may no longer be readable, though, so clear only when you mean it.

    This is also the way out of an inheritance that is stuck: clearing removes the adopted identity so a fresh inherit (or a fresh machine) can start.
