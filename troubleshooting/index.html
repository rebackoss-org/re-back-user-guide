    Troubleshooting¶

    Start with the service status and the current screen. Most problems are one of: the web interface is not reachable, the machine account is missing, a source path is not readable, or a restore is waiting for a key.

    The web interface does not load¶

    Check that re-back is running:

    # systemd install
sudo systemctl status re-back

# Docker
docker compose ps
docker compose logs --tail=100

# Kubernetes
kubectl get pods
kubectl logs deploy/re-back --tail=100

    Then check:

    • Port: the default is 8080.
    • Address: BBAPP_ADDR=:8080 listens on all interfaces; BBAPP_ADDR=127.0.0.1:8080 listens only on localhost.
    • Firewall: allow the port only from the network you trust.
    • Docker port mapping: 8080:8080 publishes it; 127.0.0.1:8080:8080 keeps it local.
    • Kubernetes: the manifest has no Ingress. Use kubectl port-forward deploy/re-back 8080:8080.

    If the service is running but the page is blank, reload once and check the browser console. If it still fails, include the service log in a bug report.

    Sign-in or machine account creation fails¶

    • Confirm the email and password by signing in at Backblaze directly.
    • For 2FA, use the current code; codes expire quickly.
    • Confirm the machine can reach Backblaze over HTTPS.
    • If the account already has a machine for this installation, do not create another one. Check the Machine account card first.
    • If the account is new, confirm Computer Backup is available on it.

    Repeated failed sign-ins can be rate-limited by Backblaze. Wait before trying again.

    Backup will not start¶

    Check these in order:

    1. Machine account exists. The Home screen should show a linked machine. If not, complete initial setup.
    2. At least one volume exists and its source path exists. A missing mount or a typo in the path means there is nothing to scan.
    3. The service user can read the source. On a systemd install the default is root. If you chose --user re-back, test with sudo -u re-back ls -la /path/to/source.
    4. Another run is already active. The status card will say so. Wait for it to finish or stop it.
    5. Paused is not the same as stopped. Paused blocks only automatic daemon runs; Start should still work.
    6. The daemon is off. That is fine for manual backups; press Start.

    Read the error line on the Backup screen. It usually names the failing path or the server response.

    The first backup is taking a very long time¶

    The first run reads and uploads the whole selection. That is expected.

    Things that help:

    • Let it run; stopping and starting does not lose completed work.
    • Raise Upload threads gradually if the machine and network have headroom.
    • Check the Scan load threshold; a low value can slow scanning on a busy machine.
    • Check free space for re-back's state; a full state disk stops progress.
    • Check the upload bandwidth outside re-back.

    Do not delete the index or state to make it faster. That forces a full re-upload and can make the server treat the volume as new.

    Files are missing from the backup¶

    Check, in order:

    1. Global include list. Empty means everything; a non-empty list limits the selection.
    2. Volume include list. If present, it replaces the global include list for that volume.
    3. Excludes. Excludes always win. A pattern like *.tmp or a plain substring can match more than you intended.
    4. Native mandatory excludes. This is on by default and skips files the native Backblaze client skips. Turn it off only if you deliberately want those files.
    5. Permissions. A file the service cannot read is skipped. This is common with 0700 home directories when running as a non-root user.
    6. Mount marker. If Require .bzre_mounted is on and the marker is missing, the whole volume is skipped.
    7. The file is on a different volume than the one you configured.

    After changing filters, save the configuration and run another backup. Filters apply on the next scan, not to a run already in progress.

    A network volume vanished and the backup looks like it deleted everything¶

    Stop the backup first.

    1. Check that the NFS/SMB mount is actually present.
    2. Remount it at the same path.
    3. Confirm the files are visible from the host.
    4. For the future, enable Require .bzre_mounted on that volume and create the marker file at the mount root.

    Do not delete the machine account or the state directory to "reset" this. That can turn a temporary mount problem into a permanent identity problem. If the server has already recorded deletions, contact the project with the run details before taking destructive action.

    Restore will not start¶

    Message or symptom Check
    Asked to sign in Restore always needs an account sign-in, even for this machine
    No machines in the list Confirm the account and that the machine has completed a backup
    "a restore is already running" Wait for the current restore or let it finish; only one runs at a time
    Locked machine Enter the backup key for that machine
    Key rejected Use the exact passphrase; there is no recovery reset
    Destination error Use a writable path with enough free space
    Docker/Kubernetes restore writes nowhere useful The destination must be a mounted path visible inside the container or pod

    Restore finished but files are wrong or unreadable¶

    • If the backup uses a key, confirm you used the correct one.
    • Check the restore status for skipped files, partial files, or warnings.
    • Try restoring to a different empty folder rather than in place.
    • For a failing local disk, use Restore in place with Force full download so existing bad chunks are not trusted.
    • Keep the failed output until you have a good restore; do not overwrite it.

    The backup key is lost¶

    There is no recovery reset. The data encrypted with that key cannot be restored without it. Search your password manager and any escrow copy you made when the key was created.

    If you still have access to the machine and its saved key, export or record the key before changing anything. Do not remove the key from the account hoping to make old data readable; removal affects future backups, not existing encrypted data.

    Docker or Kubernetes sees the wrong paths¶

    The source path in re-back is the path inside the container or pod, not the host path.

    • Docker: if you mount /mnt/photos on the host to /mnt/photos in the container, configure /mnt/photos.
    • Docker: if the host path is different, use the container side of the mount.
    • Kubernetes: add a volume and volume mount to the Deployment, then use that mount path.

    The same rule applies to restore destinations. A destination that is not mounted will be written inside the container's temporary filesystem and may disappear when the container is replaced.

    Where the files live¶

    Install method Configuration State and logs
    Install script / systemd /etc/re-back/config.json /var/lib/re-back, /var/log/re-back
    Native binary BBAPP_CONFIG_DIR BBAPP_STATE_DIR, BBRE_API_LOG
    Docker /config in the container /data in the container
    Kubernetes /data/config in the pod /data/state in the pod

    State includes the machine identity, file index, backup history, and restore history. Treat it as sensitive and do not delete it during ordinary troubleshooting.

    Before opening an issue¶

    Include:

    • the re-back version shown in the interface,
    • the install method (systemd, binary, Docker, Kubernetes),
    • what you expected and what happened,
    • the exact error text,
    • a short, redacted log excerpt.

    Remove account emails, passwords, 2FA codes, backup keys, machine IDs, and any private file paths before posting.
